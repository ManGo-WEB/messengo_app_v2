## 1. Концепция продукта

**Messengo V2** — независимое SaaS-приложение «одного окна» (единый Inbox) для бизнеса:
мультитенантный агрегатор мессенджеров, в котором клиент (организация) подключает свои
аккаунты и каналы и отвечает на входящие сообщения из всех мессенджеров в едином интерфейсе.

Ключевые отличия от V1 (E:\PROJECTS\агрегатор_мессенджеров_с_rag, messengo.ru):

| Аспект | V1 | V2 (этот проект) |
|---|---|---|
| Приложение | Эволюция одного Next.js-приложения | Новое приложение с нуля, отдельный репозиторий |
| UI | Минималистичный собственный CSS | Новый интерфейс по линии прототипа (референс Umnico): дашборд, чаты, интеграции, профиль |
| Каналы | VK, Telegram (бот + личный), Meta (FB/IG) | Те же + WhatsApp и MAX через Green API |
| AI/RAG | Отсутствует (только в видении) | Полноценная поэтапная реализация (раздел 6) |
| Переиспользование | — | Обкатанные механики и подходы адаптеров V1, документация по интеграциям (папка Docs) |

Решение зафиксировано владельцем продукта (2026-11-04): путь «Б» — новый UI как независимое
приложение с нуля; из V1 переносим проверенные решения, а не код сервиса целиком.

## 2. Целевые пользователи и сценарии

- **Организация-клиент (тенант)**: владелец аккаунта, подключает каналы, управляет подпиской, загружает базу знаний.
- **Оператор**: работает в едином Inbox — читает входящие, редактирует/принимает AI-черновики (этап 2), отвечает вручную, на этапе 3 — наблюдает и контролирует автоответы, принимает эскалации.
- Основной сценарий дня оператора: открыть Inbox → список диалогов по всем каналал в одном списке → открыть диалог → увидеть историю, контакт, черновик AI (этап 2+) → отправить ответ.

Начальное ограничение (унаследованное из V1): одна организация = один админ/оператор.
Несколько операторов на организацию — будущее расширение (раздел 9).

## 3. Каналы и способы подключения

### 3.1. Переносимые из V1 (обкатанные, подтверждены live)

| Канал | Механизм (проверен в V1) |
|---|---|
| **ВКонтакте** | OAuth 2.0 через id.vk.ru (PKCE) → выбор сообщества → Callback API (вебхук) → отправка `messages.send`. Подтверждено live 2026-10-08. |
| **Telegram (бот канала)** | Bot API (собственный тонкий клиент на fetch): публикации + комментарии через связанную группу; каждое обсуждение — отдельная ветка Inbox. |
| **Telegram (личный аккаунт, Secretary Mode)** | Подключение личного аккаунта через business/bot-привязку. Подтверждено live 2026-10-06. |
| **Instagram Direct, Facebook Messenger** | Meta Graph API v25.0: OAuth (Facebook Login), вебхуки, User/Page Access Token. Обмен подтверждён live 2026-10-16. Ограничения: 24-часовое окно ответов, App Review / Advanced Access — обязательный этап для продакшена. |

### 3.2. Новые каналы через Green API

Green API — единый REST-шлюз с вебхуками (например `incomingMessageReceived`), официальный
провайдер WhatsApp API (WABA). Подробности: `Интеграция через Green-Api.md`.

| Канал | Механизм |
|---|---|
| **WhatsApp** | Инстанс Green API (QR-подключение устройства либо WABA). Тариф Developer на этапе разработки → партнёрский аккаунт при масштабировании. |
| **MAX** | Нативная интеграция Green API (анонс апреля 2026). Подключение «как устройство» через QR. |

### 3.3. Проверенный факт по Instagram/Facebook (важно)

По публичным данным green-api.com, Green API нативно поддерживает только **WhatsApp,
Telegram и MAX**. Нативной поддержки Instagram/Facebook не найдено; Instagram упоминается
только через сторонний no-code коннектор (Make.com), что для продукта неприемлемо.
Поэтому **Instagram и Facebook подключаются через Meta Graph API** — адаптер уже обкатан в V1.
Если появится информация о нативной поддержке IG/FB в Green API (например, от их поддержки) —
решение пересматривается.

### 3.4. Архитектурный слой каналов

- Единый контракт адаптера канала (по образцу V1: `adapter.ts` + `registry.ts`):
  - `connect` (OAuth-флоу или QR-флоу Green API),
  - `receive` (вебхук → нормализованное InboundEvent),
  - `send` (нормализованный исходящий → API канала),
  - `disconnect` / удаление данных (для Meta — обязательный флоу data deletion).
- Нормализация: любой канал приводит входящее к единой модели (канал, внешний ID, контакт, текст, вложение, метка ветки/темы).
- Тестовый адаптер (dev-only, в production отключён) — как в V1.

## 4. Механика работы приложения (ядро)

### 4.1. Поток входящего сообщения

1. Вебхук канала (VK Callback API / Telegram Bot API / Meta webhook / Green API webhook) попадает на единый endpoint приёма.
2. **Идемпотентный приём**: дедупликация по внешнему ID события (в V1 — таблица InboundEvent; подход переносим).
3. Нормализация адаптером → создаётся/обновляется Контакт и Диалог (Conversation).
4. Сообщение сохраняется в историю, диалог поднимается в Inbox.
5. Этап 2+: событие ставится в очередь на генерацию AI-черновика (раздел 6.2).
6. Этап 3+: событие уходит в конвейер автоответа (раздел 6.3).

### 4.2. Поток исходящего сообщения

- Outbox-паттерн поверх PostgreSQL (проверен в V1, без Redis/брокера на старте):
  отправка = задание OutboxJob с попытками (claim/attempt/recover/reconcile), статус
  «unknown» при неопределённости результата, ревизии черновиков с обнаружением конфликта
  редактирования.
- Ручной ответ: оператор пишет текст → задание в Outbox → фоновый worker отправляет → статус и история попыток видны оператору.

### 4.3. Inbox (главный экран оператора)

- Единый список диалогов всех каналов с фильтрами по каналу/статусу.
- Панель диалога: история, карточка контакта, ветки (для Telegram-обсуждений), композер.
- Черновики: ручные и AI (этап 2+), с различимой маркировкой источника.
- Уведомления о новых входящих (по образцу прототипа: NotificationPanel).

### 4.4. Подключение каналов (экран «Интеграции»)

- VK: кнопка → OAuth → выбор сообщества.
- Telegram-бот: ввод токена бота.
- Telegram-личный: Secretary Mode флоу (по образцу V1).
- WhatsApp / MAX: мастер Green API — создание/верификация инстанса через API, показ QR, ожидание сканирования, статус сессии.
- Instagram / Facebook: OAuth Facebook Login + выбор Page/аккаунта.

### 4.5. Мультитенантность и безопасность (переносим из V1)

- Изоляция всех данных по organizationId на уровне каждого запроса.
- Шифрование секретов каналов (ключ шифрования в окружении — по образцу CHANNEL_SECRET_KEY V1).
- Аудит изменений через БД-триггеры.
- Идемпотентность вебхуков, at-least-once доставка Outbox.
- Флоу удаления данных (обязателен для Meta, распространяем на все каналы).

## 5. Архитектура V2 (замысел)

- **Стек (зафиксировано владельцем 2026-11-04)**: **Next.js** — одна кодовая база для UI и API (переиспользование экспертизы V1). **Визуальный язык берём из прототипа V2** (React-прототип по референсу Umnico): дизайн-токены в одном файле, примитивы Button/Badge/Tabs/Toggle/Stepper/FilterChip, тёмный сайдбар, экраны Чаты / Каналы связи / Оплаты / Воронка / Задачи / Настройки. Прототип коллеги — источник дизайн-системы и моков, переносимых на рельсы Next.js.
- **V1 и V2 движутся параллельно** (зафиксировано): развитие V1 приостановлено, клиенты с messengo.ru **не мигрируются** (их там нет); в дальнейшем на серверах, где хостится messengo.ru, будет залита чистая версия V2.
- **Backend**: собственный API-сервер + фоновый worker (по образцу V1: приём вебхуков, Outbox, джобы Green API/Meta, heartbeat).
- **БД**: PostgreSQL. Единая модель данных (диалог/контакт/сообщение/подключение канала/outbox/inbound) + таблицы RAG (этап 2): документы, чанки, embeddings (pgvector).
- **Очереди**: на старте — Outbox поверх PostgreSQL (проверено в V1); Redis/BullMQ — только если возникнет реальная потребность.
- **Аутентификация**: email+пароль, сессии, организации (в V1 обкатан Better Auth — кандидат на переиспользование подхода).
- **Развертывание**: Docker Compose, CI/CD по образцу V1 (checks → deploy VDS, миграции, бэкапы).

Базовая модель данных (эволюция схемы V1, ~34 модели): Organization, User, ChannelConnection
(+профили VK/Telegram/Meta/GreenApi), Conversation, Message, Draft, OutboxJob, InboundEvent,
SendAttempt, KnowledgeDocument, DocumentChunk, AiDraft, AutoReplyLog (новые для этапов 2–3).

## 6. AI/RAG — поэтапный план (зафиксировано владельцем 2026-11-04)

> Поправка владельца: «сначала AI-черновик без базы знаний» — неверный путь.
> Запускаем приложение одного окна, затем подключаем RAG-базу; черновики — сразу на базе знаний.

### 6.1. Этап 1 — Одно окно (без AI)

- Полный цикл: подключение каналов, входящие, единый Inbox, ручные ответы, черновики, статусы доставки.
- Цель: обкатать ядро и каналы Green API (WhatsApp, MAX) без риска для клиентов.

### 6.2. Этап 2 — RAG-черновики (период тестирования)

- Организация загружает базу знаний. **Форматы на старте (зафиксировано): Markdown, PDF, Word (DOCX), TXT**; Excel — на перспективу.
- Пайплайн: ingestion → chunking → embeddings (pgvector) → retrieval → генерация черновика LLM.
- На каждое входящее сообщение AI готовит **черновик ответа** с указанием использованных фрагментов знаний (цитаты-источники — обязательны для доверия оператора).
- **Решение об отправке всегда за оператором**: принять / отредактировать / отклонить / запросить новый черновик.
- Сбор метрик качества: доля принятых без правок, доля отклонённых, время экономии оператора.

### 6.3. Этап 3 — Автоответы (после тестирования и отладки)

- AI отвечает автоматически на базе знаний; **оператор остаётся наблюдателем и контролёром**.
- Обязательные механизмы безопасности:
  - порог уверенности ретривера: ниже порога — эскалация оператору, автоответ не отправляется;
  - полный лог каждого автоответа (что найдено, что отвечено, уверенность);
  - кнопка «вмешаться» / перевод диалога в ручной режим в один клик;
  - плавный перевод канала на автоматику: сначала автоответ только на простые категории обращений, расширение по мере подтверждённого качества;
  - ограничение частоты автоответов одному контакту (анти-спам страховка).
- Роль оператора на этом этапе: наблюдение, контроль, обработка эскалаций, пополнение базы знаний по итогам разбора неудачных ответов.

## 7. Нефункциональные требования

- Надёжность: идемпотентный приём вебхуков, at-least-once отправка, восстановление worker после сбоя (обкатано в V1).
- Приватность: шифрование секретов, флоу удаления данных, изоляция тенантов; для Meta — соответствие требованиям App Review.
- Стоимость Green API: тариф Developer на разработке; расчёт posуточной тарификации инстансов — в `Интеграция через Green-Api.md`; партнёрская модель — при росте числа клиентов.
- Адаптивность UI от ~520px до широких экранов (требование из V1 сохраняется).

## 8. Что сознательно НЕ входит в V2 на старте

- Вложения и голосовые сообщения (только текст; как и в V1 MVP).
- Несколько операторов на организацию, роли и права.
- Исходящие рассылки/кампании.
- Автоперевод, аналитика отчётов сложнее базовых.
- Подтверждение email / восстановление пароля (переносится из V1 как быстрая задача).

## 9. Дорожная карта (укрупнённо)

1. **Фаза A**: каркас V2 (репозиторий, бэкенд-каркас, БД, аутентификация, модель данных).
2. **Фаза B**: перенос механик каналов из V1 (VK, Telegram ×2, Meta) на новые рельсы.
3. **Фаза C**: интеграция Green API (WhatsApp, затем MAX) — QR-мастер подключения, приём/отправка.
4. **Фаза D**: новый UI (Inbox, интеграции, профиль, уведомления) поверх готового API.
5. **Фаза E**: этап 2 RAG — загрузка документов, пайплайн, AI-черновики в Inbox, метрики.
6. **Фаза F**: этап 3 — автоответы с эскалациями и плавным расширением автоматизации.
7. **Фаза G**: закрытие вопросов App Review Meta, партнёрский тариф Green API, несколько операторов.

## 10. Монетизация (предварительно, схема не фиксируется)

Обсуждённые варианты (в т.ч. с коллегой в чате прототипа V2):

- **Оплата за подключение отдельных каналов** — базовая рассматриваемая модель. В прототипе коллеги реализован экран «Оплаты»: тарифная сетка каналов (26 позиций), карта «Мой тариф» со степперами количества подключений, выбор периода оплаты со скидками:
  - месяц — базовая цена;
  - полгода — −10%;
  - год — −35%;
  - 2 года — −50%;
  - предупреждение «не оплачен тариф» (red alert) при просрочке.
- **Отдельная оплата API-ключа для подключения LLM-провайдера** (этапы 2–3 RAG) — оплата AI-функциональности отдельно от каналов.

Конкретная схема монетизации на дату PRD **не зафиксирована** — экран «Оплаты» прототипа закладываем в UI как каркас, цены и итоговый состав тарифов определяются позже.

## 11. LLM-провайдер для RAG (предварительно)

Предпочтительный вариант владельца: **OpenAI, размещённый/проксируемый на серверах в России** (конкретный провайдер-посредник ещё не выбран). Зафиксировано на 100%: будет использоваться **один общий API-ключ для нескольких LLM-моделей**, при этом модели имеют **OpenAI-совместимый API**. Архитектурное следствие: LLM-слой за единой абстракцией с OpenAI-совместимым контрактом и конфигурацией «ключ + список моделей» — модели и провайдера можно менять без переписывания пайплайна RAG; выбор конкретной модели (например, дешёвая для черновиков / сильная для сложных диалогов) — параметр настройки.
