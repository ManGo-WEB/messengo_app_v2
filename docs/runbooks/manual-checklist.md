# Чеклист ручной сквозной проверки каналов (план C4 п.2)

Прогон выполняется на рабочем сервере с публичным HTTPS-URL (🖥 серверная
приёмка по правилу №5 плана): вебхуки, OAuth-редиректы и QR-подключения
требуют внешних соединений. По каждому каналу проходится полный цикл:
**подключение → входящее → исходящее → отключение**.

Порядок прогона фиксируется в таблице в конце документа (дата, исполнитель,
результат). Автоматический e2e-сценарий на фикстурах — `tests/e2e/`
(`bun x playwright test`), он не требует сервера и не заменяет этот чеклист.

## 0. Подготовка

- [ ] Приложение задеплоено на сервер (`docs/runbooks/deploy.md`, `deploy-v2.md`), `/api/health` отвечает `{"status":"ok"}` и показывает живость worker
- [ ] `.env` на сервере заполнен ключами каналов (см. `.env.example`: VK_\*, TELEGRAM_\*, META_\*, GREEN_API_\*)
- [ ] HTTPS-домен и адреса вебхуков доступны снаружи (VK Callback API, Telegram setWebhook, Meta hub.challenge, Green API webhookUrl)
- [ ] Регистрация организации и вход оператора работают; `/api/channels` отдаёт пустой список подключений
- [ ] Автотест e2e на стенде зелёный (`bun x playwright test`) — базовая механика приёма/отправки исправна

## 1. TESTING-канал (локальный, без сервера)

- [ ] Подключение: создаётся автоматически при первом событии (`POST /api/testing/inbound`), статус ACTIVE
- [ ] Входящее: событие → Contact, Conversation, Message (status RECEIVED); повтор события → дедупликация
- [ ] Исходящее: ответ через `POST /api/conversations/:id/messages` → воркер → SENT, externalId заполнен
- [ ] Отключение: `DELETE /api/channels/:id` → DISCONNECTED, секреты затёрты

## 2. VK (Callback API) — runbook: `vk.md`

- [ ] **Подключение**: OAuth через id.vk.ru (PKCE) → выбор сообщества → статус ACTIVE; токен, confirmation-строка и секрет Callback API сохранены зашифрованно
- [ ] **Входящее**: сообщение сообщества от реального пользователя → диалог в Inbox, имя контакта корректно; повтор вебхука → дубля нет
- [ ] **Исходящее**: ответ доставляется в VK (messages.send, токен сообщества); статус SENT; у получателя видно отправителя
- [ ] **Отключение**: DISCONNECTED, секреты затёрты; события VK после отключения не попадают в систему

## 3. Telegram-бот — runbook: `telegram-bot.md`

- [ ] **Подключение**: ввод токена бота (+ опционально имя канала со связанной группой) → getMe проходит, setWebhook установлен, статус ACTIVE; неверный токен → понятная ошибка 400
- [ ] **Входящее**: личка бота → отдельный диалог; комментарий под постом связанной группы → отдельная диалог-ветка (threadTitle = заголовок поста)
- [ ] **Исходящее**: ответ в личку доставляется; ответ в обсуждение доставляется как reply к сообщению; статус SENT
- [ ] **Отключение**: deleteWebhook выполнен, статус DISCONNECTED

## 4. Telegram-личный (Secretary Mode) — runbook: `telegram-personal.md`

- [ ] **Подключение**: deeplink служебного бота → бизнес-привязка личного аккаунта → подключение ACTIVE, связка telegram-user-id → ChannelConnection
- [ ] **Входящее**: личное сообщение от собеседника → диалог; два разных собеседника → два разных диалога
- [ ] **Исходящее**: ответ доставляется от имени служебного бота в чат с собеседником; статус SENT
- [ ] **Отключение**: привязка снимается, статус DISCONNECTED; новые сообщения собеседников не теряются молча (понятная ошибка/статус)

## 5. Facebook Messenger — runbook: `meta.md`

- [ ] **Подключение**: Facebook Login (скоупы pages_messaging и пр.) → выбор Page → подписка вебхуков страницы → ACTIVE, Page Access Token зашифрован
- [ ] **Входящее**: сообщение от пользователя страницы → диалог; проверка подписи X-Hub-Signature-256 (неверная → 403); hub.challenge-верификация отвечает
- [ ] **Исходящее**: ответ доставляется (`/me/messages`); при диалоге старше 24ч отправка блокируется с понятной ошибкой оператору
- [ ] **Отключение**: DISCONNECTED; страница data-deletion (`/api/meta/data-deletion/[code]`) открывается

## 6. Instagram Direct — runbook: `meta.md`

- [ ] **Подключение**: тот же OAuth Meta → выбор профессионального аккаунта → ACTIVE
- [ ] **Входящее**: DM от пользователя → диалог; дедупликация повторов
- [ ] **Исходящее**: ответ доставляется через Instagram Messaging API; 24-часовое окно соблюдается
- [ ] **Отключение**: DISCONNECTED, ссылка на удаление данных доступна

## 7. WhatsApp через Green API — runbook: `whatsapp-greenapi.md`

- [ ] **Подключение**: создание инстанса → QR отображается оператору → скан с телефона → состояние authorized → ACTIVE; неавторизованный инстанс 10+ минут → статус ERROR у подключения
- [ ] **Входящее**: incomingMessageReceived → диалог (chatId → Contact); идемпотентность повторных уведомлений
- [ ] **Исходящее**: ответ доставляется (Green API sendMessage); таймаут → UNKNOWN, затем reconcile по outgoingMessageStatus; failed → FAILED с причиной
- [ ] **Отключение**: DISCONNECTED, инстанс деактивируется/затирается; напоминание о «телефон должен выходить в сеть раз в 14 дней» учтено в инструкции оператору

## 8. MAX через Green API — runbook: `max-greenapi.md`

- [ ] **Подключение**: создание инстанса → QR → при включённой 2FA запрос кода пробрасывается оператору (PENDING_2FA → ввод кода → ACTIVE)
- [ ] **Входящее**: событие входящего сообщения MAX → диалог; типы событий соответствуют актуальной документации Green API
- [ ] **Исходящее**: ответ доставляется; статус SENT/FAILED корректен
- [ ] **Отключение**: DISCONNECTED, инстанс деактивируется

## 9. Общие проверки после прогона каналов

- [ ] Изоляция тенантов: подключение/диалог чужой организации недоступны (404), `/api/channels` показывает только свои
- [ ] Статусы отправок во всех каналах записаны в SendAttempt; при сетевом сбое — UNKNOWN и reconcile не дублируют отправку
- [ ] `GET /api/channels/:id/status` показывает последнюю ошибку вебхука/отправки и время последнего входящего
- [ ] Все затёртые при отключении секреты не расшифровываются (пустой шифр-текст)
