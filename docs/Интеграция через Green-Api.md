### 🏗️ Архитектура многоканального приложения «Одно окно»

Чтобы объединить WhatsApp, Telegram и MAX в едином интерфейсе, предлагается следующая архитектура. Она опирается на две ключевые возможности GREEN-API: **унифицированные исходящие методы** и **вебхуки для входящих событий**.

#### Ключевые компоненты системы

1. **Frontend (Агентское окно)**
   Единый интерфейс для операторов или менеджеров. В нём отображаются все диалоги из разных мессенджеров в одном списке. Каждый диалог помечен иконкой канала (WhatsApp, Telegram, MAX), но логика работы с ним одинакова.
2. **Backend-приложение (Ядро системы)**
   Сервер, который выполняет роль оркестратора:
   - Принимает команды от Frontend (отправить сообщение, загрузить историю).
   - Управляет инстансами GREEN-API (по одному или несколько на каждый канал).
   - Принимает и обрабатывает **вебхуки** от GREEN-API.
3. **Слой адаптеров (Унификация)**
   Хотя GREEN-API уже унифицировал API, полезно создать собственный легкий слой нормализации. Он приводит входящие вебхуки и сущности (чат, отправитель, сообщение) к единой внутренней модели данных. Это позволит в будущем легко добавить новый канал (например, Instagram или WABA), не переписывая логику ядра.
4. **Хранилище данных**
   База данных для хранения:
   - Унифицированных диалогов и сообщений.
   - Метаданных инстансов (какой `idInstance` какому каналу и аккаунту соответствует).
   - Справочников контактов и статусов.

#### Поток данных (как это работает)

**Входящее сообщение (от клиента):**
Клиент пишет в WhatsApp, Telegram или MAX → GREEN-API получает сообщение и отправляет **вебхук** (`incomingMessageReceived`) на ваш сервер → Ваш Backend принимает вебхук, извлекает `typeInstance` (например, `whatsapp`, `telegram`, `max`) и приводит сообщение к единому формату → Сообщение сохраняется в БД и через WebSocket (или SSE) мгновенно отображается в едином окне оператора.

**Исходящее сообщение (от оператора):**
Оператор пишет ответ в едином окне → Frontend отправляет запрос на ваш Backend → Backend определяет, к какому каналу относится диалог, и вызывает соответствующий метод GREEN-API (например, `sendMessage`) с нужным `idInstance` → GREEN-API доставляет сообщение в мессенджер клиента.

#### Унификация форматов входящих событий

Хотя структура вебхуков GREEN-API едина, полезно выделить общие поля, которые есть для всех каналов. Например, в вебхуке для входящего сообщения (`incomingMessageReceived`) всегда присутствуют:

- `instanceData.idInstance` — идентификатор инстанса.
- `instanceData.typeInstance` — **тип мессенджера** (`whatsapp`, `telegram`, `max`).
- `senderData.chatId` — идентификатор чата.
- `senderData.senderName` — имя отправителя.
- `messageData.typeMessage` — тип сообщения (`textMessage`, `imageMessage` и т.д.).
- `messageData.textMessage` — текст сообщения (если применимо).

Эти поля позволяют вашему приложению работать с сообщением, не задумываясь о его происхождении. Например, для Telegram в ответе метода `GetMessage` также возвращаются `chatId`, `typeMessage`, `textMessage` и другие поля, аналогичные WhatsApp и MAX.

### 🧑‍💻 Тариф «Developer»: бесплатный доступ для разработки

**«Developer» — это не тип аккаунта, а бесплатный тарифный план**, который можно выбрать внутри обычного личного кабинета. Он предназначен для знакомства с сервисом, тестирования и отладки интеграции.

**Ключевые ограничения тарифа «Developer» (на примере WhatsApp и MAX):**

- **Лимит чатов:** Взаимодействие и получение уведомлений доступно только для **3 чатов** (контактов или групп).
- **Лимит инстансов:** В личном кабинете можно создать только **1 инстанс** с этим тарифом.
- **Лимиты на методы:** Многие методы API имеют месячные лимиты запросов (например, `checkWhatsapp` — 100 запросов, `getChatHistory` — 300, `getAvatar` — 100).
- **Отмена лимита на отправку:** Важное уточнение: с 2023 года ограничение на *количество отправляемых* сообщений было снято. Лимит в 3 чата касается именно *взаимодействия* (диалогов), а не общего числа исходящих сообщений.

**Для чего подходит:** Идеально для **первоначальной разработки, тестирования и отладки** вашего многоканального приложения. Документация прямо рекомендует программистам использовать отдельный аккаунт и инстансы на тарифе Developer для настройки интеграции.

### 🤝 Партнёрский аккаунт: промышленная интеграция

**Партнёрский аккаунт — это отдельный тип аккаунта** (его можно проверить в консоли: `Профиль -> Информация о аккаунте -> Тип аккаунта -> Партнерский`). Он предназначен для компаний (CRM, SaaS-провайдеров), которые строят свой бизнес на интеграции с GREEN-API и работают с **большим количеством инстансов** на своей стороне.

**Ключевые особенности и преимущества:**

- **Управление инстансами через API:** Создание и удаление инстансов можно автоматизировать, а не делать вручную в консоли.
- **Постоплатная система:** Взаимодействие с клиентами происходит по постоплате (со второго месяца).
- **Непрерывная работа:** Инстансы продолжают работать даже при отрицательном балансе, включая создание новых инстансов.
- **Посуточная тарификация:** Оплата списывается ежедневно в 00:00 UTC+3 за созданные и не удалённые инстансы.
- **Выделенная поддержка:** Персональный менеджер и выделенный канал поддержки.
- **White Label:** Возможность работы под вашим брендом.

**Важное ограничение:** Партнёрская схема несовместима с тарифом Business. Если в вашем аккаунте уже есть инстансы Business, их тарификация останется стандартной. Документация рекомендует после получения партнёрского ключа удалить все старые инстансы и создавать новые через API.

### 🛠️ Создание инстанса через API (партнёрский аккаунт)

В партнёрском аккаунте вы получаете специальный `partnerToken` и можете управлять инстансами программно.

- **Создание:** Вы вызываете метод `createInstance`, передавая в нём настройки для нового инстанса (например, `name`, `webhookUrl` и другие). В ответ вы получаете `idInstance` и `apiTokenInstance` для этого нового инстанса.
- **Мониторинг готовности:** Сразу после создания инстанс не готов к работе. Вам нужно опрашивать его статус методом `getStateInstance` каждые 5 секунд, пока он не перейдёт в состояние `notAuthorized`. Это будет означать, что инфраструктура инстанса на стороне GREEN-API готова, и его можно авторизовывать.

### 🔑 Авторизация (верификация) инстанса

Вот ключевой момент, который отвечает на ваш вопрос. **Статус `notAuthorized` — это не конец, а начало процесса авторизации для каждого конкретного инстанса.** GREEN-API не может автоматически «верифицировать» аккаунт мессенджера без вашего участия (или участия вашего пользователя).

Процесс выглядит так:

1. **Получение QR-кода:** Как только инстанс перешёл в статус `notAuthorized`, ваше приложение должно начать запрашивать для него QR-код, вызывая метод `QR` (рекомендуется делать это каждые 2 секунды, чтобы код был актуальным).
2. **Сканирование:** Этот QR-код необходимо отобразить конечному пользователю (например, в вашем интерфейсе «одного окна»). Пользователь должен отсканировать его из соответствующего мобильного приложения (WhatsApp, Telegram или MAX), чтобы привязать свой аккаунт к этому конкретному инстансу.
3. **Альтернативы:** Для WhatsApp и Telegram также существует возможность авторизации по номеру телефона (через методы `getAuthorizationCode` / `SendAuthorizationCode`), но для MAX, судя по последним релизам, основным и поддерживаемым способом является именно QR-код.
4. **Завершение:** После успешного сканирования запросы QR-кода нужно прекратить. Инстанс переходит в статус `authorized` и готов к отправке и получению сообщений.

### 💎 Итог: Верификация на уровне инстанса, а не пользователя

Таким образом, в вашей будущей SaaS-модели **верификация будет происходить на уровне каждого отдельного инстанса**, а не один раз для каждого пользователя.

- Пользователь регистрируется в вашем сервисе.
- Он хочет подключить, например, свой WhatsApp. Ваша система через партнёрский API создаёт для него **новый инстанс**.
- Ваша система получает для этого инстанса QR-код и показывает его пользователю.
- Пользователь сканирует код, и **этот конкретный инстанс** становится авторизованным.
- Если тот же пользователь захочет подключить ещё и Telegram, ваша система создаст для него **ещё один, новый инстанс**, и процедура с QR-кодом повторится уже для него.

То есть `partnerToken` даёт вам право создавать «коробки» (инстансы) оптом, но «ключи» к каждой из них (авторизацию) пользователям всё равно придётся вставлять по отдельности.

### 💵 Базовый расчёт стоимости одного инстанса

Партнёрский тариф использует **посуточную модель оплаты**. Базовая ставка, согласно официальной документации GREEN-API, составляет **$0.40 в день** за один инстанс. В рублёвом эквиваленте это **от 23 рублей в день**.

Исходя из этого, базовая месячная стоимость одного инстанса (для ровного счёта взят 30-дневный месяц) составит:

- **В долларах:** $0.40 × 30 = **$12.00 в месяц**.
- **В рублях:** 23 ₽ × 30 = **690 ₽ в месяц**.

Эта стоимость является «сырьевой» ценой для вас как для партнёра. Она не включает вашу наценку, налоги и другие операционные расходы. Конечная цена для вашего пользователя будет определяться вашей бизнес-моделью, но именно **$0.40/день (≈$12/мес)** — это ваша себестоимость за каждый активный инстанс.

### 📉 Скидки за объём: как они работают

GREEN-API официально подтверждает наличие **объёмных скидок (Volume discounts)** для партнёров. Ключевой принцип: **чем больше клиентов и используемых инстансов, тем ниже стоимость каждого отдельного инстанса для партнёра**.

На основе доступных материалов можно выделить следующие ориентиры:

- **Максимальный размер скидки:** В официальном блоге GREEN-API, посвящённом стоимости WhatsApp Business API в 2026 году, указано, что **«при больших объёмах скидки достигают 25%»**.
- **Порог входа для партнёрской программы:** Чтобы получить доступ к партнёрской схеме и, соответственно, к возможности получать объёмные скидки, необходимо **подключить не менее 50 клиентов**. Это важное условие, которое фактически является отправной точкой для получения статуса партнёра.
- **Индивидуальный подход:** Точные пороги объёма, с которых начинают действовать скидки и их градация (например, скидка 5% на 100 инстансов, 10% на 500 и т.д.), в открытой документации не детализированы. Они обсуждаются **индивидуально с отделом продаж (sales@green-api.com)**.

### 🏗️ Рекомендуемая архитектура бэкенда

Хотя React и PostgreSQL — отличный фундамент, для обработки вебхуков от GREEN-API вам понадобится **серверный слой (бэкенд)**. Вы не можете полагаться на фронтенд в этом вопросе, так как вебхуки — это HTTP-запросы, которые GREEN-API отправляет на ваш сервер.

**Рекомендуемый бэкенд: Node.js**

Почему именно Node.js?

- **Официальная поддержка:** GREEN-API предоставляет официальные SDK для Node.js (JavaScript/TypeScript). Это упростит интеграцию.
- **Эффективная обработка вебхуков:** Node.js с его неблокирующей моделью ввода-вывода хорошо справляется с большим количеством одновременных HTTP-запросов, что важно при потоке вебхуков от множества инстансов.
- **Единый язык:** Использование JavaScript/TypeScript и на фронтенде (React), и на бэкенде (Node.js) упрощает разработку и позволяет переиспользовать некоторые модели данных или логику.

**Ключевые компоненты бэкенда:**

1. **Веб-сервер (например, Express или Fastify):** Для приёма вебхуков от GREEN-API и предоставления REST API для вашего React-фронтенда.
2. **Обработчик вебхуков:** Это отдельный модуль или сервис, который принимает POST-запросы от GREEN-API. **Критически важно:** GREEN-API ожидает, что ваш сервер ответит статусом `200 OK` в течение 180 секунд, иначе он повторит отправку. Ваш обработчик должен быстро подтверждать получение и асинхронно ставить задачу на обработку в очередь.
3. **Очередь задач (например, Redis + BullMQ):** Для надёжной обработки входящих сообщений. Вебхук-сервер только принимает уведомление и кладёт его в очередь, а отдельный «воркер» (процесс) занимается дедупликацией, сохранением в базу и другими действиями. Это предотвращает потерю данных и позволяет обрабатывать пиковые нагрузки.
4. **WebSocket-сервер (например, [Socket.io](https://socket.io/)):** Для доставки новых сообщений в реальном времени на React-фронтенд. Когда воркер обработал входящее сообщение и сохранил его в базу, он отправляет событие через WebSocket, и интерфейс оператора мгновенно обновляется.

### 🗄️ Работа с PostgreSQL: важные нюансы

PostgreSQL — отличный выбор, но для системы обмена сообщениями есть несколько моментов, которые стоит учесть заранее.

- **Идемпотентность и дедупликация:** Поскольку GREEN-API может повторно отправлять вебхуки, ваш бэкенд должен уметь распознавать дубликаты. В документации GREEN-API рекомендуется использовать уникальный идентификатор сообщения для фильтрации уже обработанных уведомлений. В PostgreSQL можно создать **уникальный индекс** на поле с идентификатором сообщения (например, `idMessage`). При попытке вставить дубликат база данных выбросит ошибку, которую вы сможете перехватить и проигнорировать. Это самый надёжный способ.
- **Производительность при пиковых нагрузках:** При большом количестве одновременных вебхуков соединения с PostgreSQL могут стать «узким горлышком». Для production-окружения настоятельно рекомендуется использовать **PgBouncer** — пул соединений, который ставится перед базой данных и эффективно переиспользует соединения между вашим бэкендом и PostgreSQL.
- **Хранение истории сообщений:** PostgreSQL хорошо подходит для хранения истории. Однако для очень больших объёмов данных (миллионы сообщений) стоит подумать о **партиционировании** таблицы сообщений по дате или по идентификатору инстанса. Это ускорит запросы к «свежим» данным и упростит архивацию старых.

### 🏗️ Архитектура RAG-модуля для вашего приложения

Ваша система уже имеет правильную точку входа — обработчик вебхуков. RAG-логика встраивается как дополнительный слой обработки перед сохранением сообщения или его отправкой оператору.

**Поток данных для входящего сообщения с RAG:**

1. **Вебхук от GREEN-API** поступает на ваш Node.js-бэкенд (как и раньше).
2. **Оркестратор RAG** (новый сервис в вашем бэкенде) перехватывает сообщение. Он определяет, к какому **тенанту** (пользователю вашего сервиса) и **инстансу** относится диалог.
3. **Поиск в векторной базе знаний**: Оркестратор преобразует текст входящего сообщения в вектор (embedding) и ищет в базе знаний **только этого конкретного тенанта** наиболее релевантные фрагменты (чанки) информации.
4. **Формирование промпта**: Найденные фрагменты (контекст) вместе с исходным вопросом клиента и системной инструкцией (например, «Ты — вежливый ассистент компании X. Отвечай только на основе предоставленного контекста») собираются в единый промпт.
5. **Вызов LLM**: Промпт отправляется в выбранную вами языковую модель (OpenAI GPT, Gemini, локальная модель и т.д.) для генерации ответа.
6. **Маршрутизация ответа**:
   - В режиме **«Автоответчик»** сгенерированный текст через GREEN-API (`sendMessage`) отправляется клиенту.
   - В режиме **«Ассистент»** сгенерированный текст сохраняется в вашей базе как **черновик** и по WebSocket отправляется в интерфейс оператора для проверки и отправки.

### 🗄️ Реализация базы знаний на PostgreSQL

Ваш выбор PostgreSQL оказывается как нельзя кстати. Вам не нужно вводить отдельную векторную базу данных, так как в PostgreSQL есть расширение **`pgvector`**. Оно позволяет хранить векторы (embeddings) прямо в таблицах и выполнять семантический поиск с помощью специальных индексов (например, HNSW).

**Пайплайн загрузки знаний пользователем (Ingestion):**

1. **Загрузка**: Пользователь в вашем интерфейсе загружает документ (PDF, DOCX, TXT).
2. **Парсинг**: Ваш бэкенд извлекает из него текст (для PDF можно использовать библиотеки вроде `pdf-parse`).
3. **Чанкинг (Chunking)**: Текст разбивается на небольшие смысловые фрагменты (например, по 512-1024 токена с небольшим перекрытием в 128 токенов). Практика показывает, что небольшие и сфокусированные чанки работают лучше, чем большие блоки.
4. **Векторизация (Embedding)**: Каждый чанк превращается в вектор с помощью модели эмбеддингов (например, от OpenAI или Google).
5. **Сохранение**: Вектор вместе с текстом чанка и метаданными (ID пользователя, имя файла) сохраняется в таблицу PostgreSQL с колонкой типа `VECTOR`.

### 🔐 Критически важный аспект: Мультитенантность и изоляция данных

Это самый важный пункт. Ваша система является **мультитенантной** (multi-tenant), так как вы обслуживаете множество пользователей. База знаний каждого пользователя должна быть строго изолирована. Ответ бота, основанный на документах одного клиента, не должен случайно попасть к другому.

В документации по архитектуре таких систем (например, от Microsoft и в открытых руководствах) описано несколько подходов. Для вашего случая, с PostgreSQL, есть элегантное и надёжное решение.

**Рекомендуемый подход: Изоляция на уровне строк (Row-Level Security, RLS) в PostgreSQL**

Вы можете использовать один общий экземпляр PostgreSQL и даже одну таблицу для векторов всех пользователей, но включить в ней **политику безопасности на уровне строк (RLS)**.

- В каждой строке (каждом чанке) будет колонка `tenant_id` (ID пользователя вашего сервиса).
- Политика RLS автоматически гарантирует, что при запросе от имени `tenant_id = 123` база данных вернёт **только те строки**, где `tenant_id = 123`.
- Даже если в коде вашего приложения произойдёт ошибка и вы забудете добавить фильтр по `tenant_id` в SQL-запрос, **сама база данных** не позволит вернуть данные другого пользователя.

Это обеспечивает надёжную защиту от утечки данных между пользователями и при этом эффективно использует ресурсы, не требуя создания отдельной базы данных для каждого клиента.

### 💎 Итог

Да, вы сможете реализовать RAG-бота для каждого пользователя. Ваша архитектура будет выглядеть так:

1. **Фронтенд (React)**: Интерфейс для загрузки документов в базу знаний, настройки режима работы бота (автоответчик/ассистент) и просмотра сгенерированных черновиков.
2. **Бэкенд (Node.js)**: Новый **RAG-оркестратор**, который обрабатывает входящие вебхуки, выполняет поиск в базе знаний и вызывает LLM.
3. **База данных (PostgreSQL + `pgvector`)**: Хранит все данные, включая изолированные базы знаний пользователей с политикой **Row-Level Security**.

GREEN-API уже имеет SDK и демонстрационные библиотеки для создания ботов с интеграцией GPT на Node.js, что упростит вам начало разработки. Таким образом, вы не просто можете это сделать, а ваш текущий стек технологий является одним из наиболее подходящих для этой задачи.
