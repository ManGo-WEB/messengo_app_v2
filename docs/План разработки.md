## 0. Правила работы (обязательны для каждого пункта плана)

1. **Workflow**: один пункт (или тесно связанная группа пунктов) = одна фича = одна ветка. Имена веток: `feat/a1-karkas-nextjs`, `fix/b3-telegram-webhook` и т.п. по ID пункта. По завершении — pull request в `main` (заголовок и описание на русском), слияние только после прохождения проверок.
2. **Коммиты и PR — на русском языке.**
3. **Среда разработки (зафиксировано владельцем)**: WSL под Windows 11. Docker установлен на хосте; отдельный Ubuntu-контейнер внутри Docker НЕ нужен — Docker-образ и есть дистрибутив, WSL используется как рабочая среда для Docker и инструментов. Все команды разработки выполняются из WSL.
4. **Рантайм (зафиксировано владельцем)**: **Bun**. Код должен разворачиваться и корректно работать под управлением Bun: локально — в Docker-контейнерах на базе образа `oven/bun`, на сервере — так же. Из этого следует: менеджер пакетов `bun` (lock-файл `bun.lock`), запуск `bun run ...`, скрипты не должны полагаться на особенности Node-рантайма; при выборе зависимостей проверять совместимость с Bun.
5. **Серверные фазы (зафиксировано владельцем)**: пункты, требующие внешних соединений и калбэков (OAuth-редиректы VK/Meta, вебхуки с публичным URL, QR-подключения Green API), локально проверяются только на моках/фикстурах; их приёмка с реальными сервисами проводится на рабочем сервере (доступы предоставит владелец позже — до этого момента соответствующие КП помечаются «ожидает серверной проверки»). Такие пункты помечены в плане значком 🖥.
6. **Каждый пункт заканчивается критериями приёмки (КП)** — субагент не завершает работу, пока все локальные КП не выполнены и не проверены.
7. **Источники знаний** (читать перед задачей):
   - `docs/PRD.md` — концепция и зафиксированные решения;
   - V1: `E:\PROJECTS\агрегатор_мессенджеров_с_rag` — образцы реализации (адаптеры, Outbox, аутентификация, CI); код V1 написан под Node.js — при переносе механики адаптировать под Bun;
   - `docs/Интеграция через Green-Api.md`, `docs/Схема подключения *.md` — механика каналов.
8. **Секреты** — только через `.env` (шаблон в `.env.example`), никогда в коде и коммитах.
9. **Определение готовности фазы**: все пункты слиты в main, проверки CI зелёные, серверные КП (🖥) закрыты или явно помечены «ожидает серверной проверки», фаза отмечена в таблице прогресса ниже.

## ФАЗА A. Каркас приложения

Цель: работающий скелет Next.js + БД + аутентификация + CI, на котором строятся все остальные фазы.

### A1. Каркас Next.js и базовая структура

**Ветка**: `feat/a1-karkas-nextjs`

Инструкции субагенту:
1. Создать в корне репозитория приложение: **Next.js (последняя стабильная версия, App Router) + TypeScript strict**, установка и запуск через **Bun** (`bunx create-next-app`, `bun install`, `bun run dev`). Tailwind не подключать — стили по дизайн-токенам прототипа (см. Фазу D); на этом этапе один минимальный `globals.css`.
2. Убедиться, что lock-файл — `bun.lock` (не package-lock.json); команды запуска в `package.json`-скриптах должны работать под Bun. Проверить запуск под Bun внутри Docker: `docker run --rm -v $PWD:/app -w /app oven/bun bun run dev` поднимается без ошибок Node-специфики.
3. Создать структуру каталогов (пустые с `README.md`-заглушкой в 1 строку, чтобы вошли в git):
   - `src/app` — страницы и API-роуты;
   - `src/components` — UI-компоненты;
   - `src/server` — серверный код: `auth/`, `channels/`, `db/`, `secrets/`;
   - `src/worker` — фоновый процесс;
   - `prisma/` — схема БД;
   - `docs/` — уже существует;
   - `tests/unit/`, `tests/integration/`, `tests/e2e/`.
4. Настроить ESLint + Prettier (в стиле V1: `eslint.config.mjs` из V1 как образец), добавить скрипты `lint`, `typecheck` (`tsc --noEmit`), `test` (Bun test runner: `bun test`, тесты в стиле `bun:test`; если для интеграционных тестов удобнее node:test — допускается, но запуск должен идти через `bun test --preload` либо отдельный скрипт под Bun), `dev`, `build`.
5. Добавить `.gitignore` (node_modules, .next, .env, coverage), `.editorconfig`.
6. README.md в корне: название проекта, стек (Next.js + Bun + PostgreSQL + Prisma), как запустить в WSL/Docker (кратко, 20–30 строк).

**КП**: `bun run dev` в WSL поднимает дефолтную страницу `/api/health` (отвечает `{"status":"ok"}`); то же работает в контейнере `oven/bun`; `lint` и `typecheck` проходят без ошибок; структура каталогов в репозитории; `bun.lock` закоммичен.

### A2. PostgreSQL + Prisma: базовая модель данных

**Ветка**: `feat/a2-bd-prisma` (зависит от A1)

Инструкции:
1. Добавить зависимости: `prisma`, `@prisma/adapter-pg` (образец — V1 `package.json` / `prisma.config.ts`).
2. `prisma/schema.prisma`: провайдер postgresql, создать первые модели (все с `organizationId` там, где это данные тенанта):
   - `Organization { id, name, createdAt }`
   - `User { id, email (unique), passwordHash, name, organizationId, role }` (на старте роль только `admin` — один оператор на организацию, см. PRD §2);
   - `ChannelConnection { id, organizationId, type (enum: VK, TELEGRAM_BOT, TELEGRAM_PERSONAL, FACEBOOK, INSTAGRAM, WHATSAPP, MAX, TESTING), externalId, status (enum: PENDING, ACTIVE, ERROR, DISCONNECTED), config (Json — зашифрованные секреты), createdAt, updatedAt }`;
   - `Conversation { id, organizationId, connectionId, contactId, threadTitle (nullable), lastMessageAt }`;
   - `Contact { id, organizationId, connectionId, externalId, name, avatarUrl }`;
   - `Message { id, organizationId, conversationId, direction (IN/OUT), text, status (enum: RECEIVED, PENDING, SENT, FAILED, UNKNOWN), externalId, createdAt }`;
   - `InboundEvent { id, organizationId, connectionId, externalEventId, payload (Json), processedAt (nullable) }` — уникальный индекс `(connectionId, externalEventId)` для идемпотентности;
   - `OutboxJob { id, organizationId, messageId, attempts, status, nextAttemptAt, lastError }`;
   - `SendAttempt { id, outboxJobId, result, detail, createdAt }`;
   - `Draft { id, organizationId, conversationId, text, revision, source (enum: MANUAL, AI), updatedAt }`.
3. Настроить `docker-compose.yaml`: сервис `db` (postgres:18, пароль/пользователь из `.env`, порт не публиковать наружу в prod-композе; dev — публиковать на localhost). Продублировать как `compose.production.yaml` по образцу V1 (позже наполнится).
4. `.env.example`: `DATABASE_URL`, `AUTH_SECRET`, `CHANNEL_SECRET_KEY` (комментарий: ключ шифрования секретов каналов).
5. Миграция: `prisma migrate dev --name init`. Скрипт `db:migrate` в package.json.

**КП**: `docker compose up -d db` + `npm run db:migrate` создают все таблицы; `npx prisma validate` без ошибок.

### A3. Аутентификация (регистрация, вход, сессии)

**Ветка**: `feat/a3-auth` (зависит от A2)

Инструкции:
1. Подключить **Better Auth** с Prisma-адаптером (образец — V1 `src/server/auth`; дополнительные модели в схему Prisma по требованию библиотеки).
2. Регистрация: email + пароль → создаются `User` и его `Organization` в одной транзакции. Валидация: email-формат, пароль ≥ 8 символов.
3. API-роуты: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` (текущий пользователь + организация).
4. Хелпер `src/server/auth/session.ts`: `requireSession(request)` → возвращает `{ user, organization }` или 401. **Все** защищённые роуты используют только его.
5. Пароль хранится только хешем (как предлагает Better Auth), логи не содержат паролей и хешей.
6. Integration-тест: регистрация → логин → `/api/auth/me` возвращает пользователя; доступ без сессии к защищённому роуту → 401.

**КП**: тесты проходят; повторная регистрация того же email → 409; `/api/auth/me` без сессии → 401.

### A4. Фоновый worker + Outbox-механика

**Ветка**: `feat/a4-worker-outbox` (зависит от A2)

Инструкции (механика переносится с V1, `src/worker/main.ts` V1 — образец):
1. `src/worker/main.ts`: отдельный процесс, запускаемый Bun (`bun run src/worker/main.ts`, скрипт `dev:worker`; prod — `bun build src/worker/main.ts --target bun --outdir dist/worker`). Цикл: раз в 2 секунды выбирает due-задания.
2. Алгоритм обработки OutboxJob (claim → attempt → result):
   - claim: атомарно (`UPDATE ... WHERE status='PENDING' AND nextAttemptAt <= now() ... RETURNING`) пометить задание за воркером, чтобы несколько воркеров не конфликтовали;
   - attempt: вызвать зарегистрированный обработчик по типу задания (реестр обработчиков `src/worker/handlers.ts`; на этом этапе один обработчик-заглушка `echo`, пишущий в лог);
   - успех → `Message.status = SENT`; ошибка → попытка +1, `nextAttemptAt` с экспоненциальной задержкой (1мин → 2 → 4 → ... максимум 5 попыток), после исчерпания → FAILED;
   - каждая попытка пишется в `SendAttempt`;
   - «unknown»: если сеть оборвалась во время отправки — статус UNKNOWN, отдельный reconcile-проход проверяет фактическую доставку (заготовка интерфейса на будущее, пока просто фиксируется статус).
3. Heartbeat: worker каждые 30 сек пишет метку времени в таблицу (или файл — по образцу V1); API `GET /api/health` показывает живость worker.
4. `Dockerfile` на базе **`oven/bun`** (многостадийный: development → runtime; и web, и worker запускаются через Bun) + сервис `worker` в `docker-compose.yaml`.
5. Integration-тест: создать OutboxJob вручную → воркер обрабатывает → Message SENT, SendAttempt создан; задание с падающим обработчиком → 5 попыток → FAILED.

**КП**: тесты проходят; `docker compose up` поднимает web+worker+db; health отражает статус worker.

## ФАЗА B. Каналы из V1: VK, Telegram (бот + личный), Meta

Цель: приём и отправка сообщений по 4 каналам V1 на новом каркасе. Каждый канал = свой PR. Перед задачей субагент обязан изучить соответствующий код V1 (`E:\PROJECTS\агрегатор_мессенджеров_с_rag\src\server\channels\<канал>` и runbook в `docs/runbooks/` V1) и переносить механику, а не переписывать с нуля.

### B0. Контракт адаптера канала

**Ветка**: `feat/b0-adapter-contract` (зависит от A4)

Инструкции:
1. `src/server/channels/adapter.ts` — интерфейс (TypeScript), который реализует каждый канал:
   - `type: ChannelType`;
   - `initiateConnect(organizationId, params): Promise<ConnectResult>` — старт флоу подключения (OAuth-ссылка / создание инстанса);
   - `completeConnect(organizationId, callbackParams): Promise<ChannelConnection>` — завершение (OAuth-код, QR-скан и т.п.);
   - `parseWebhook(headers, body): InboundNormalized[]` — валидация подписи + разбор события в нормализованный вид `{ externalEventId, contact: {externalId, name}, conversationKey, threadTitle?, text, occurredAt }`;
   - `sendMessage(connection, text): Promise<SendResult>` где `SendResult = { status: 'SENT', externalId } | { status: 'FAILED', error } | { status: 'UNKNOWN', externalId? }`.
2. `src/server/channels/registry.ts` — реестр `Map<ChannelType, Adapter>`; worker и вебхуки получают адаптер только через реестр.
3. Общий пайплайн приёма (один для всех каналов), `src/server/channels/pipeline.ts`:
   - дедупликация по `(connectionId, externalEventId)` в `InboundEvent` (идемпотентность);
   - upsert `Contact` и `Conversation` (ключ — contact+connection, для веток — threadTitle);
   - insert `Message(direction=IN, status=RECEIVED)`;
   - диспетчеризация событий дальше (хук `onMessageReceived` — пустой на этом этапе, займёт RAG в Фазе E).
4. Универсальный роут вебхука `POST /api/webhooks/[channel]`: находит активное подключение организации → адаптер.parseWebhook → pipeline. Секреты подключений расшифровываются хелпером из A6/B-задач (`src/server/secrets/store.ts`, AES-шифрование, ключ `CHANNEL_SECRET_KEY`, образец — V1).
5. Unit-тесты pipeline с фейковым адаптером: дубликат события не создаёт второе сообщение; создаётся Contact+Conversation+Message.
6. `TESTING`-адаптер (dev-only, образец V1 `testing-adapter.ts`): принимает события через `POST /api/testing/inbound` и пишет их в pipeline; отключается флагом `NODE_ENV=production`.

**КП**: тесты pipeline зелёные; testing-канал позволяет вручную создать диалог без реального мессенджера.

### B4. Meta: Facebook Messenger + Instagram Direct 🖥 (серверная приёмка: Facebook Login и вебхуки Meta)

**Ветка**: `feat/b4-meta` (зависит от B0; образцы V1: `channels/meta/`, `channels/facebook/adapter.ts`, `channels/instagram/adapter.ts`, runbooks Meta; ограничения — `docs/Схема подключения Facebook и Instagram.md`)

Инструкции:
1. ## ФАЗА E. RAG: база знаний и AI-черновики (этап 2 PRD)

Цель: оператор загружает документы, на каждое входящее AI готовит черновик с цитатами; отправка — только оператором.

### E1. Модель данных и хранение знаний

**Ветка**: `feat/e1-knowledge-model`

1. Prisma-модели: `KnowledgeDocument { id, organizationId, filename, format (MD/PDF/DOCX/TXT), status (PROCESSING/READY/FAILED), raw (текст), createdAt }`; `DocumentChunk { id, documentId, organizationId, ordinal, text, embedding vector }` — подключить **pgvector** (расширение PostgreSQL; миграция `CREATE EXTENSION vector`; Prisma-тип для vector — unsupported/raw, доступ через raw SQL, как принято с pgvector+Prisma). Индекс HNSW на embedding.
2. API: `POST /api/knowledge/upload` (multipart, форматы MD/PDF/DOCX/TXT, лимит 20 МБ; Excel — отвергать с понятной ошибкой «на перспективе»), `GET /api/knowledge` (список + статусы), `DELETE /api/knowledge/:id`.
3. Unit-тесты валидации форматов и лимитов.

**КП**: загрузка MD-файла → статус READY после обработки; PDF >20МБ → 413.

### E2. Пайплайн обработки: chunking + embeddings

**Ветка**: `feat/e2-chunk-embed` (зависит от E1)

1. Обработчик в worker: извлечение текста (MD/TXT — напрямую; PDF — `pdf-parse` или аналог; DOCX — mammoth), нормализация (очистка переносов, пустых строк).
2. Chunking: по 800–1200 символов с перекрытием 150, не разрывая заголовки Markdown (для MD — резать по структуре заголовков, где возможно).
3. Embeddings через LLM-шлюз (E4, реализовать сначала интерфейс, здесь — вызов): батчами по 64 чанка, retry на 429.
4. Статусы документа PROCESSING → READY / FAILED (текст ошибки оператору).
5. Integration-тест: MD-документ → чанки с embedding-заглушкой → READY.

**КП**: тест зелёный; упавший шлюз → документ FAILED с причиной, повторная обработка по кнопке.

### E3. LLM-шлюз (единый ключ, OpenAI-совместимый)

**Ветка**: `feat/e3-llm-gateway` (зависит от A3; PRD §11)

1. `src/server/llm/gateway.ts`: единая абстракция `embed(texts)`, `chat(messages, { model })`. Конфигурация организации: **один API-ключ на несколько OpenAI-совместимых моделей** — таблица `LlmConfig { organizationId (unique), baseUrl, apiKey (зашифровано), models: Json (список: {id, назначение: embed|draft|fallback}) }`. Управление — из «Настроек» (D5, включить поле).
2. `POST /api/llm/test-key` — проверка ключа: запрос списка моделей `/v1/models` и тестовый chat-вызов.
3. Никаких hardcoded-провайдеров: только baseUrl+ключ из конфига. Secret в логи не пишется (маскировать).
4. Unit-тесты на моках; integration — с локальным OpenAI-совместимым мок-сервером.

**КП**: ключ сохраняется зашифрованно; test-key реально вызывает указанный baseUrl.

### E4. Retrieval + генерация черновика

**Ветка**: `feat/e4-rag-draft` (зависит от E2, E3, B0-хук onMessageReceived)

1. На каждое входящее (хук из B0, `AiDraftJob` в Outbox-механике): retrieval — top-k=6 чанков по косинусному сходству (pgvector `<=>`), фильтр по организации; k и порог — параметры конфига.
2. Промпт генерации: системный промпт (роль — ассистент поддержки организации, отвечает в тоне диалога, только на основе фрагментов, язык — язык клиента), контекст: последние 10 сообщений диалога + фрагменты с маркерами источников [1]..[6].
3. Ответ модели → `AiDraft { conversationId, text, sources (Json: chunkId+цитата), confidence }`; в UI черновик показан отдельным блоком с бейджем «AI-черновик», кнопками: Принять (в композер), Отредактировать, Отклонить, «Новый черновик».
4. Отказы: ретривер ниже порога → черновик не создаётся, пометка «нет релевантных знаний» (данные для метрики).
5. Двухуровневые модели (PRD §11): модель `draft` — по умолчанию; если у организации назначена сильная модель `draft_strong` — использовать при длине истории > N сообщений.
6. Integration-тест с мок-LLM: входящее → черновик с источниками; без релевантных чанков → отказ.

**КП**: тест зелёный; черновик в UI содержит цитаты-источники; исходящее помечено `source: AI` (Draft.source) при отправке принятого черновика.

### E5. Метрики этапа тестирования

**Ветка**: `feat/e5-rag-metrics` (зависит от E4)

## ФАЗА F. Автоответы (этап 3 PRD)

Цель: автоматические ответы на базе знаний; оператор — наблюдатель и контролёр. Вход только после накопления метрик этапа E (решение владельца).

### F1. Конфигурация и правила автоматики

**Ветка**: `feat/f1-auto-config`

1. Модель `AutoReplyConfig { organizationId (unique), enabled, confidenceThreshold (default 0.75), maxRepliesPerContactPerDay (default 5), allowedCategories (Json, null = все) }`.
2. UI в Настройках: тумблер «Автоответы», порог, лимиты; предупреждение о рисках.
3. Тесты валидации.

### F2. Конвейер автоответа и эскалации

**Ветка**: `feat/f2-auto-pipeline` (зависит от F1, E4)

1. Продолжение пайплайна E4: если `enabled` и confidence ≥ порога и лимиты не исчерпаны и категория разрешена → авто-отправка черновика (Message.source = AI_AUTO, пометка в UI бейджем «Авто»).
2. Ниже порога / лимит / неразрешённая категория → диалог помечается `needsOperator=true`, уведомление в NotificationPanel, диалог поднимается в фильтр «Эскалации».
3. `AutoReplyLog { organizationId, messageId, aiDraftId, confidence, decision, sentAt }` — каждая автоматика логируется.
4. Кнопка «Перевести в ручной режим» на диалоге (individual override) и «вмешаться» во время генерации.
5. Анти-зацикливание: автоответ не триггерит новый автоответ тому же контакту чаще 1 раза в 5 минут.
6. Integration-тесты: выше порога — автоотправка; ниже — эскалация; лимит — эскалация.

### F3. Пост-контроль оператора

**Ветка**: `feat/f3-supervision` (зависит от F2)

1. Экран/фильтр «Автоответы»: лента всех автоответов с источниками и confidence; действия: «Успешно», «Ошибка» (ошибка создаёт задачу пополнения базы знаний — связь с экраном Задачи).
2. Дашборд-виджет «Автоответы»: доля успешных, доля эскалаций, средний confidence.
3. Плавное расширение: вкл/выкл автоматики по категориям обращений (классификация — промпт-шаг в F2, категория сохраняется в логе).

### F4. Стресс-проверка безопасности

1. Тесты: контакт-спамер упирается в лимиты; при недоступности LLM — все диалоги в эскалацию, сервис не падает; unknown-отправки не дублируются.
