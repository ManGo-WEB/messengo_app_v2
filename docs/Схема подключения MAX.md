## 📱 Принцип: почему «устройство», а не «бот»

У MAX есть два принципиально разных пути интеграции:

1. **Официальный Bot API** — требует создания бота на партнёрской платформе MAX (доступно только юридическим лицам) и передачи его API-токена в настройки интеграции. Это надёжный, но ограниченный сценарий: вы общаетесь с пользователями от имени **бота**, а не от имени их личного аккаунта.
2. **Подключение как устройства (веб-сессия)** — приложение авторизуется в MAX так же, как это делает веб-версия `web.max.ru` или десктопный клиент. Пользователь сканирует QR-код, и ваша платформа становится ещё одним «устройством» в его аккаунте. Именно этот способ использует Umnico для подключения MAX как канала.

Для сценария «каждый пользователь подключает свой мессенджер» подходит **второй путь**. Он не требует, чтобы пользователь был юридическим лицом, и позволяет работать с его существующим аккаунтом.

## 🧩 Компоненты архитектуры

### 💻 Клиентская часть (frontend)

- Кнопка **«Подключить MAX»** в разделе каналов.
- Отображение QR-кода, полученного от бэкенда, и состояния ожидания сканирования.
- Опрос (polling) или WebSocket-канал для получения статуса: `ожидание` → `сканирован` → `успех` / `ошибка` / `требуется 2FA`.

### ⚙️ Серверная часть (backend)

- **Сервис авторизации MAX** — управляет жизненным циклом QR-сессий.
- **Хранилище сессий** — привязывает учётные данные MAX-устройства к внутреннему `user_id` вашего приложения.
- **Обработчик событий** — слушает входящие сообщения от MAX (через WebSocket или long-polling) и нормализует их в общий формат вашего агрегатора.
- **Менеджер устройств** — позволяет пользователю видеть подключённые MAX-аккаунты и отключать их (что должно приводить к завершению сессии на стороне MAX).

### 🔌 Интеграционный слой с MAX

Для QR-авторизации используется **внутренний API MAX**, а не официальный Bot API. В сообществе существуют reverse-engineered библиотеки, которые абстрагируют эту логику:

- **`webmaxsocket` (Node.js)** — поддерживает QR-авторизацию, работу через WebSocket и TCP, управление сессиями и устройствами (аналог «Профиль → Устройства»).
- **`max-account-api` (Node.js)** — клиент для личных аккаунтов MAX, который явно позиционируется как «как `node-telegram-bot-api`, но для вашего собственного аккаунта MAX» и поддерживает вход по QR-коду.
- **`maxapi-python` / `PyMax`** — аналогичные решения на Python с поддержкой QR-авторизации веб-клиента.

> **Важно:** использование внутреннего API несёт риски, связанные с возможными изменениями на стороне MAX. Umnico, судя по всему, идёт именно по этому пути для канала MAX как устройства, но для бот-интеграции использует официальный API-токен. Вам стоит предусмотреть мониторинг и возможность быстрого переключения на официальный Bot API, если он станет доступен для вашего сценария.

## 🪜 Пошаговая реализация (для бэкенда)

### 🟢 Шаг 1. Инициализация QR-сессии

Ваш бэкенд создаёт новую сессию авторизации через библиотеку внутреннего API MAX и получает данные для QR-кода (обычно это URL или специальный токен, который кодируется в QR).

### 🔵 Шаг 2. Отображение QR и ожидание

QR-код передаётся на фронтенд. Бэкенд параллельно слушает событие подтверждения от MAX (через тот же WebSocket-канал, который используется для авторизации).

### 📲 Шаг 3. Сканирование и подтверждение на телефоне

Пользователь выполняет действия в приложении MAX: **«Профиль» → «Устройства» → «Войти по QR-коду»** → сканирует код. На этом этапе MAX может запросить подтверждение входа или 2FA-пароль, если он включён.

### 🔑 Шаг 4. Получение и сохранение сессии

После успешного сканирования библиотека возвращает учётные данные сессии (токен, идентификатор устройства и т.д.). Бэкенд должен:

1. Сохранить эти данные в зашифрованном виде в хранилище, привязав к `user_id` вашего приложения.
2. Запустить фоновый процесс (воркер) для этой сессии, который будет слушать входящие сообщения.
3. Уведомить фронтенд об успехе, чтобы интерфейс показал канал как подключённый.

### 💬 Шаг 5. Приём и отправка сообщений

Воркер, использующий сохранённую сессию, принимает события о новых сообщениях и передаёт их в вашу общую шину/очередь. Исходящие сообщения от пользователя вашего приложения отправляются через тот же сессионный клиент.

### 🗑️ Шаг 6. Отключение (опционально, но важно)

Пользователь должен иметь возможность отключить MAX-аккаунт в вашем приложении. Это должно приводить к **завершению сессии на стороне MAX**, чтобы устройство исчезло из списка доверенных в его аккаунте. Библиотеки вроде `webmaxsocket` предоставляют методы для управления сессиями (например, `closeAllSessionsExceptCurrent`).

## ⚠️ Нюансы, которые стоит учесть

### 🔐 Двухфакторная аутентификация (2FA)

Umnico отдельно предупреждает: для стабильной работы интеграции необходимо, чтобы в настройках безопасности MAX **двухфакторная аутентификация была отключена или корректно настроена для сторонних сессий**. В вашей схеме нужно либо предусмотреть обработку запроса 2FA (если библиотека это поддерживает), либо явно просить пользователя отключить 2FA перед подключением, либо документировать это как известное ограничение.

### 📜 Правовые и policy-риски

Использование внутреннего API MAX для доступа к личному аккаунту может нарушать пользовательское соглашение мессенджера. Umnico, вероятно, берёт эти риски на себя, но в вашем продукте стоит юридически оценить допустимость такого подхода. Официальный Bot API лишён этого недостатка, но требует создания бота и доступен только юрлицам.

### 📈 Масштабирование сессий

Каждый подключённый пользователь — это отдельная активная сессия MAX. Вам потребуется:

- Хранилище сессий с возможностью горизонтального масштабирования.
- Механизм продления/refresh сессий (некоторые библиотеки поддерживают периодический `sync()`).
- Обработка отзыва сессии со стороны MAX (например, если пользователь завершил все сеансы на другом устройстве).

### 🧪 Тестирование и мониторинг

Поскольку внутренний API может меняться, критически важен слой абстракции: ваш код не должен быть жёстко завязан на конкретную библиотеку. Предусмотрите health-check для каждой активной сессии и алерты при массовых сбоях авторизации или приёма сообщений.

### ✅ Почему это работает: возможности библиотек

Вы будете использовать не официальный Bot API, а внутренний API MAX (как и Umnico). Reverse-engineered библиотеки для работы с личным аккаунтом предоставляют доступ к тем же функциям, что и обычное приложение.

- **`webmaxsocket` (Node.js)**: Библиотека явно поддерживает **группы и каналы**. В её возможностях указано: «Группы и каналы: создание, инвайты, админы, участники, ссылки...». Для отправки сообщений есть отдельные методы: `sendMessage` (для чатов и групп) и **`sendMessageChannel`** (специально для каналов). Также есть метод **`getChats()`**, который возвращает список чатов пользователя.
- **`max-account-api` (Node.js)**: Позиционируется как клиент для личного аккаунта, который позволяет «получать сообщения, отвечать... создавать группы». В разделе возможностей указано управление чатами и группами: «Создание групп / каналов, добавление / удаление участников...».
- **Библиотеки на Python (PyMax, `maxapi-python`)**: Также поддерживают работу с чатами, группами и каналами, включая отправку сообщений и управление участниками.

Таким образом, после QR-авторизации ваша сессия получает права обычного пользователя, включая возможность читать и писать в те каналы и группы, где он состоит.

### 🎛️ Как реализовать выбор каналов и групп

Сценарий, который вы описываете, полностью реализуем и выглядит следующим образом:

1. **QR-авторизация**: Пользователь сканирует код, и ваш бэкенд получает активную сессию, привязанную к его аккаунту MAX.
2. **Получение списка чатов**: Сразу после авторизации ваш бэкенд вызывает метод `getChats()` (или аналогичный), чтобы получить перечень всех диалогов, групп и каналов, в которых состоит пользователь. В ответе каждый чат будет иметь тип: `dialog`, `chat` (группа) или `channel`.
3. **Интерфейс выбора**: Вы передаёте этот список на фронтенд. Пользователю показывается экран со списком его каналов и групп (с возможностью отфильтровать личные диалоги). Он отмечает галочками те, сообщения из которых хочет видеть в вашем общем интерфейсе.
4. **Сохранение выбора**: Выбранные идентификаторы (`chatId`) сохраняются в вашей базе данных в привязке к профилю пользователя в вашем приложении.
5. **Фильтрация потока**: Ваш воркер, слушающий события от MAX, начинает получать **все** входящие сообщения. Однако в общий inbox вашего приложения он передаёт только те, чей `chatId` есть в сохранённом списке выбранных пользователем.
6. **Отправка ответов**: Когда пользователь пишет ответ в вашем интерфейсе, вы отправляете его через соответствующий метод (`sendMessage` или `sendMessageChannel`), используя сохранённый `chatId`. Сообщение уходит от имени его личного аккаунта MAX.

### 🧐 Нюансы и ограничения (на примере Umnico)

- **Umnico поддерживает работу в группах и каналах**: В их документации прямо указано, что интеграция позволяет общаться «как в личных сообщениях, так и в групповых чатах и каналах».
- **Гибкость выбора**: Судя по обзору Umnico, их интерфейс, возможно, не предлагает пользователю детального выбора конкретных каналов и групп после подключения; интеграция, вероятно, работает со всеми доступными чатами. Однако это ограничение **интерфейса Umnico**, а не техническая невозможность. Для вашего приложения реализация экрана выбора — это вопрос дизайна продукта, а не ограничений API.
- **Риски**: Важно помнить, что использование внутреннего API несёт риски, связанные с возможной блокировкой аккаунта за «нестандартную активность» (об этом предупреждает `max-account-api`), а также с изменениями в протоколе MAX. Umnico также просит отключать 2FA для стабильной работы, что является компромиссом в безопасности.

### 💎 Итог

Предложенная вами схема не только возможна, но и является стандартной для юзербот-подходов. Вы сможете предоставить пользователям гибкий инструмент: после подключения своего аккаунта MAX по QR-коду они получат в вашем интерфейсе именно те каналы и группы, которые выберут сами, и смогут отвечать в них от своего имени.
