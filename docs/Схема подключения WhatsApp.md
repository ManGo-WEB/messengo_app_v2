### 🖥️ Схема подключения: шаг за шагом

Процесс можно разделить на два основных этапа: первоначальная авторизация и последующая работа.

#### Этап 1: Авторизация по QR-коду

Этот этап происходит один раз (или при потере сессии) и включает следующие шаги:

1. **Инициализация клиента**: Ваше приложение запускает на сервере «клиент» WhatsApp Web. Для этого используются специализированные библиотеки, которые эмулируют браузер. Примерами таких библиотек являются **`whatsapp-web.js`** (на Node.js, использует Puppeteer для управления headless-браузером) или **`Baileys`** (также на Node.js, работает напрямую через WebSocket-протокол).
2. **Генерация QR-кода**: Запущенный клиент подключается к серверам WhatsApp и получает данные для формирования QR-кода. Этот код отображается в интерфейсе вашего приложения (как в Umnico).
3. **Сканирование с телефона**: Пользователь берет свой смартфон с установленным WhatsApp и сканирует QR-код, отображенный в вашем приложении. Для этого в приложении WhatsApp нужно перейти в раздел **«Связанные устройства»** (Linked Devices) и выбрать «Связать устройство».
4. **Установка соединения и сохранение сессии**: После успешного сканирования на сервере WhatsApp происходит аутентификация. Ваш клиент получает учетные данные для входа. Критически важный момент — эти данные (токены сессии) необходимо **сохранить локально**. Это позволяет избежать повторного сканирования QR-кода при перезапуске вашего приложения или сервера.

#### Этап 2: Работа с сообщениями

После успешной авторизации и сохранения сессии ваше приложение готово к обмену сообщениями. Схема работы выглядит так:

- **Входящие сообщения**: Когда пользователь пишет на подключенный номер, серверы WhatsApp пересылают это сообщение вашему активному клиенту. Ваш клиент, в свою очередь, передает его в ваше приложение (например, через WebSocket или сохраняет в базу данных).
- **Исходящие сообщения**: Когда вы инициируете отправку сообщения из своего приложения, оно передается вашему клиенту WhatsApp Web, который отправляет его через свои серверы конечному получателю.

### ⚠️ Важные нюансы и ограничения

При реализации этой схемы важно учитывать следующие моменты, которые напрямую влияют на стабильность и безопасность:

- **Неофициальный метод**: Подключение через WhatsApp Web (эмуляция браузера) является неофициальным способом. Официальный и наиболее стабильный путь — это **WhatsApp Business API**. Сама Umnico в своей документации отмечает, что не поддерживает QR-подключение для некоторых типов интеграций и рекомендует использовать официальный API для гарантии стабильности и безопасности.
- **Риск блокировки**: Использование неофициальных методов несет риск. Meta (владелец WhatsApp) активно борется со спамом и автоматизацией. Аккаунт, подключенный через WhatsApp Web, может быть заблокирован за подозрительную активность (например, массовые рассылки).
- **Ограничение на количество устройств**: WhatsApp позволяет подключать до **четырех** связанных устройств (веб-версий или десктопных приложений) одновременно.
- **Требование к основному телефону**: Для поддержания активности связанных устройств, основной телефон должен выходить в сеть (подключаться к интернету) как минимум **раз в 14 дней**.
- **Нестабильность соединения**: Сессия WhatsApp Web может разрываться, если основной телефон отключается от интернета, находится в режиме энергосбережения или если сессия была завершена вручную с телефона.

### 🧭 Шаг 0: Выбор пути — Cloud API или BSP

Прежде чем начать, важно понять, что у вас есть два основных способа подключения, и от этого выбора зависит дальнейшая техническая реализация.

- **Meta Cloud API (прямое подключение)**: Это вариант, при котором вы интегрируетесь с API напрямую, а всю серверную инфраструктуру (хостинг, масштабирование) берет на себя Meta. - **Через BSP (Business Solution Provider)**: BSP — это официальные партнеры Meta (например, Twilio, Infobip, Wati, 360dialog). Они предоставляют готовую инфраструктуру, панели управления, поддержку и берут на себя техническую сложность. Это быстрее для старта, но вы платите за удобство в виде надбавок к тарифам Meta.

**Важное обновление**: Устаревший вариант **On-Premises API** (когда вы хостили сервер у себя) был официально упразднен 23 октября 2025 года. Все новые подключения должны использовать **Cloud API**.

Для вашего приложения, которое должно поддерживать несколько мессенджеров, прямое подключение через **Cloud API** может быть более предпочтительным, так как оно дает максимальный контроль и не создает зависимости от конкретного BSP.

Meta будет отправлять на него уведомления о новых сообщениях и статусах их доставки. В настройках приложения вы должны будете указать URL вебхука и **Verify Token** (секретное слово, которое вы придумали сами для проверки подлинности запросов от Meta).
5. **Запрос прав доступа (App Review)**: Для работы с реальными пользователями (а не только с тестовыми номерами) вашему приложению потребуется пройти проверку Meta и получить «Advanced Access» к разрешениям `whatsapp_business_messaging` и `whatsapp_business_management`. Обычно это занимает около 24 часов после верификации бизнеса.

### 💬 Шаг 3: Работа с сообщениями и шаблонами

В API действуют строгие правила коммуникации:

- **Шаблоны (Templates)**: Чтобы написать пользователю *первым*, вы обязаны использовать заранее одобренные Meta шаблоны. Они бывают трех категорий: **Marketing** (реклама), **Utility** (транзакционные уведомления, например, о заказе) и **Authentication** (коды подтверждения).
- **24-часовое окно**: Если пользователь написал вам первым, у вас есть 24 часа, чтобы отвечать ему любыми сообщениями (текст, изображения) без использования шаблонов. Это называется «customer service window».
- **Стоимость**: Meta взимает плату **за каждое доставленное сообщение**. Стоимость зависит от категории шаблона и страны получателя. Например, маркетинговое сообщение в США может стоить около **$0.025\**, а утилитарное — \**$0.0034**. Сообщения, которые пользователь отправляет вам, бесплатны. BSP, если вы через них работаете, добавляют к этой цене свою наценку.
